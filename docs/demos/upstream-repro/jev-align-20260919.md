## Can it run unattended? Yes — and the README does not say so

`AGENTS.md` says "The user supplies every label... There is no skip action", and the README
describes arrow-key menus. That reads like a hard human gate. It is not one.
`src/jev_align/cli.py:1449` falls back to a line-oriented `console.input()` whenever
`stdin` is not a TTY:

```python
if not console.is_terminal or not sys.stdin.isatty():
    choices = "/".join(label for _, label in options)
    while True:
        value = console.input(f"{prompt} ({choices}): ").strip().lower()
```

So the label picker, the rationale prompt, and the Accept/Reject/Quit gate are all drivable from
a pipe. `work/jev-align-probe/drive.py` does exactly that: it reads the rendered card, hands the
text to a caller-supplied ORACLE, and writes the answer back on stdin. Four complete optimization
runs below finished with **exit 0 and zero human keystrokes**.

The honest statement of the constraint is therefore not "it blocks". It is: **jev-align never
invents a label, and it has no flag to read labels from a dataset column.** Unattended operation
requires you to supply an oracle process. For us that is not a barrier — our gold sets are
committed files. For a genuinely unlabeled corpus it is the whole problem, unmoved.

None of the labels below are human labels, and no claim here depends on them being good.

### The defect: a dead reflection provider is presented as a clean proposal

Runs 1-3 all silently used a broken reflection model. `cli.py:75` sets
`DEFAULT_REFLECTION_MODEL = "openai/gpt-5.6-luna"` and the provider order is OpenAI → Anthropic →
Gemini, so jev-align selected OpenAI. This project's `OPENAI_API_KEY` is invalid. Probed directly
with LiteLLM:

```text
openai/gpt-5.6-luna                  -> ERROR AuthenticationError: OpenAIException -
                                        Incorrect API key provided: sk-proj-****
anthropic/claude-haiku-4-5-20251001  -> OK
```

Run 3's transcript carries **4,896** LiteLLM banners ("If you need to debug this error"). Every
single reflection call 401'd. The CLI never surfaced one of them. It rendered a full
`AI Function scores` table, a `+0.000` change, an ambiguity report, and asked
`AI Function decision (Accept/Reject/Quit)`. A total failure of the optimizer is indistinguishable,
in the UI, from "your question was already good". **jev-align's startup check verifies that a
reflection key is PRESENT, never that it WORKS.**

### The finding that decides the verdict: GEPA could not repair a wrong question

Run 4 is run 3 with a reflection model proven live in the same session
(`--reflection-model anthropic/claude-haiku-4-5-20251001`). The seed question asks about billing;
the oracle labels tickets that ask to reach a human — deliberately disjoint, the situation our
lane keeps landing in. 30 labels, 5 of them positive, 320 metric calls across two rounds:

```text
Round 1: Training F1 0.000 · P 0.000 · R 0.000 -> 0.000  (+0.000)   165/150 metric calls
Round 2: Training F1 0.000 · P 0.000 · R 0.000 -> 0.000  (+0.000)   155/150 metric calls
AI Function diff: No textual change.
```

GEPA did the work — `gepa-runs/round-0001/run_log.json` records 6 iterations × 4 tasks = **24
mutation attempts**, and `total_num_evals: 165`. Every child scored exactly what its parent
scored, so `program_candidates` still contains one entry at the end: the seed, verbatim.

The mechanism is in `src/jev_align/optimizer.py:216`. The batch-level F1 is assigned as the score
of **every row in the batch**:

```python
score = metrics.f1          # one number for the whole batch
...
results[index] = (score, {... "scores": {"correct": row_score} ...})
```

Per-row correctness is computed (`row_score`, line 202) but is carried only as auxiliary feedback;
the scalar GEPA climbs is the batch F1. When the current definition scores F1 = 0 on a minibatch —
which is precisely what a badly wrong question does — every candidate ties at 0.0, no child ever
strictly improves, and nothing is ever accepted. It is a flat-objective trap, and it bites hardest
in exactly the regime where a hand-written question most needs help. The per-row signal that would
break the tie already exists in the same function and is not used for selection
(`objective_pareto_front: {"correct": 0.333}`).

Across all four runs and roughly 800 metric calls, **GEPA produced zero textual changes to a
question.** We never observed the thing the tool exists to do.

## Fit for our extensions

Tested on our own committed ground truth rather than theirs. `work/jev-align-probe/export-failure-gold.mjs`
lifts the 11-case `CASES` table out of `work/omp-jev-failure/measure.mjs` — the same file whose
`argument` question was measured flipping HIT→MISS→MISS on byte-identical input — and emits a CSV
plus a gold sidecar. It relabels nothing; needles are grown until provably unique or it throws.
Class balance: `transient 3, argument 4, bug 4`.

Run as a multiclass task, with our three existing binary question strings reused verbatim as the
three class descriptions:

```sh
jeva optimize /tmp/jeva-ours/failure-cases.csv \
  --question "Which failure class best fits this tool failure?" \
  --column tool --column invocation --column failure \
  --class "transient=The failure is most consistent with a transient environment or dependency failure." \
  --class "argument=The failure is most consistent with a wrong argument, path, or invocation." \
  --class "bug=The failure is most consistent with a genuine bug in the code under edit." \
  --pool-size 11 --batch-size 6 --max-metric-calls 150 --seed 0
```

```text
Round 1: Training Macro-F1 1.000 · 6/6 correct -> 1.000 · 6/6 correct (+0.000)
GEPA stopped early: perfect training score · 6/150 metric calls
AI Function diff: No textual change.
```

The seed was already perfect on the labeled subset, so again GEPA changed nothing — correctly
this time. jev-align's report only covers the 6 rows it sampled, so
`work/jev-align-probe/score-ours.py` loads the saved function through the documented
`AIFunction.load(...)` runtime and scores **all 11**:

Repeated four times end to end: **11/11 every time**, including both adversarial arms, the two
cases built to punish reading the first keyword instead of the evidence. The
`adv-econnrefused-is-a-bug` arm sits at 0.26–0.37 confidence across repeats — low, but the argmax
never moved, whereas our binary `argument` question flipped HIT→MISS→MISS on byte-identical input.

**The verdict, stated against what was observed and not what the README claims:**

1. **GEPA is not the thing that helped.** It made zero textual changes in every run here. On our
   data it stopped early; on a wrong question with a live reflection model it burned 320 calls and
   accepted none of 24 mutations. Adopting jev-align *for the optimizer* is not supported by
   anything measured tonight.
2. **The task shape is the thing that helped.** Replacing three independent binary questions with
   one multiclass question over mutually-exclusive classes took our unstable `argument` signal to a
   stable 11/11 across four repeats. That restructuring needs no GEPA, no labeling loop, and no new
   dependency — it is one call shape change in `work/jev-align-probe`-style code, and it is the
   recommendation this receipt actually supports.
3. **Its acquisition and bookkeeping are worth stealing regardless**: uncertainty-ranked sampling
   plus a random audit sample, a fixed full-pool ambiguity metric comparable across rounds, and a
   persisted run directory. We currently have none of that in `work/omp-jev-*`.
4. **Do not trust its "no change" as evidence your question is good.** Three distinct causes print
   nearly the same screen: budget starvation, a dead reflection provider, and the flat-objective
   trap. Only one of the three (run 2's explicit `stopped early: perfect training score`) is
   self-announcing.

One further behaviour, not a defect but a trap: with `--pool-size 11 --batch-size 6` the run
labeled 6 rows and printed **"The unlabeled pool is exhausted"** while 5 of 11 rows had never been
offered. `cli.py:2478` treats `len(remaining) < batch_size` as exhaustion. The guard is deliberate;
the sentence is not true.

## No-claim

- **No GEPA-improved question was ever observed.** Every run ended byte-identical to its seed.
  We cannot say whether GEPA would improve a question under conditions we did not reach; we can
  only say it did not under these four.
- Runs 1–3 ran with a reflection provider that was 401ing on every call. Only run 4 had a proven
  live reflection model, and only its two rounds bear on the "can GEPA repair a wrong question"
  question. One dataset, one seed, 320 calls — not a distribution.
- **No label in this receipt is a human label.** All were produced by regexes or by our committed
  gold table via `drive.py`. jev-align is explicitly designed around human judgment, and that
  design was bypassed here to make the runs reproducible. Nothing here evaluates the quality of
  the human loop it is actually built for.
- The 11/11 on our failure cases is 11 hand-built cases from one measurement file, scored four
  times against the same gold table that defined them. It is a stability and ordering result on a
  tiny fixed set, not a generalization estimate, and there is no held-out split.
- The `--holdout` flag, `jeva functions`, resume, capture/continual-learning, and the Vercel and
  Cloudflare backends were not exercised at all.
- The `OPENAI_API_KEY` failure is a fact about this Infisical project on 2026-09-19, not about
  jev-align or about OpenAI. What is about jev-align is that it did not notice.
