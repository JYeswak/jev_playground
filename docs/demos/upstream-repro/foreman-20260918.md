## What it observes, what it decides

- **Observes:** per-worker evidence (output text, git diff/status, elapsed
  seconds, test and verification results) compressed into a bounded
  `FactoryObservation`, judged by Jev on 8 signals (complete, stuck, off-track,
  progress, tests-sufficient, verification-needed, human-needed, ready-finish).
- **Decides:** worker lifecycle via a deterministic threshold policy
  (`src/foreman/policy.py`): STOP stuck/off-track workers, RETRY with a fresh
  agent, FINISH when thresholds clear, ESCALATE to human otherwise. The demo run
  went START_VERIFIER → FINISH in ~1.4s on faked workers.

## The idleness question: NO, foreman does not implement the conductor

Grep for `queue|pending|backlog|idle` across `models/state.py`,
`observation.py`, `factory.py` returns nothing — **no pending-work concept
exists anywhere**. The policy's no-worker branch reads `not active_id` +
satisfied thresholds as FINISH. A floor with quiet panes and a non-empty ready
queue — this morning's failure — would read as DONE, the exact wrong verdict.
Foreman is a per-worker *supervisor* (is this worker's task advancing?); the
conductor problem (who works next when nobody works) is unmodeled. If it
already implemented the conductor, the tick file would be redundant. It does
not, and the tick file is not.
