# jevcache — run, not read: evaluation for this lane

**Verdict: ADOPT NARROWLY, and NEVER on the measurement harness.**
Three of the seven Jev-calling extensions may use it behind an explicit opt-in and an
isolated ledger. Two must not touch it at any setting. The measurement harness is ruled
out absolutely, by the numbers in §5. One defect found here is a tonight-problem, not a
verdict-paragraph problem: **jevcache writes 200 characters of raw, only-partly-redacted
state to a world-readable file on disk** (§6).

Everything below is from runs made on this machine for this document. Nothing is quoted
from the site except where it is being checked against a run.

## 1. What the install script actually does

Fetched and read before anything was executed:

```
curl -fsSL --max-time 25 https://jevcache.sh/install -o install.sh   # 1635 bytes
```

- **Downloads** `https://jevcache.sh/bin/jevcache-$os-$arch` — one static binary, no archive,
  no runtime, no post-install script.
- **Verifies** a SHA-256 from `$url.sha256` before installing. The check is **soft**: `want` is
  fetched with `2>/dev/null` and the comparison is inside `if [ -n "$want" ]`. If the checksum
  fetch fails or returns empty, the script installs the binary **unverified and silently**.
  That is the one thing in the file I would change.
- **Writes** exactly one file: `$BIN/jevcache`, where `$BIN` is the first of `$HOME/.local/bin`,
  `/usr/local/bin` that exists and is writable, else `$HOME/.local/bin` (created with `mkdir -p`).
  On this machine that resolved to `~/.local/bin`. It writes to a `mktemp` file first and `mv`s.
- **Does not modify PATH or any shell rc file.** It only *prints* a `note:` suggesting an export
  if `$BIN` is not already on PATH. Verified independently: `~/.zshrc`, `~/.zshenv`, `~/.zprofile`,
  `~/.profile` contain no `jevcache` string; their `~/.local/bin` PATH lines pre-date this install
  and carry unrelated comments (the rch cargo-shim history).
- **Phones home once**, at install time only:
  `curl -fsS -m3 "$BASE/api/event/install" >/dev/null 2>&1 || true`. A bare GET, no body, no
  arguments, 3-second timeout, failure ignored. It is an install counter. It is undeclared on the
  landing page, and it is the only network call in the script beyond the two downloads.
- `set -e`, no `sudo`, no `rm` outside its own tempfile, honours `JEVCACHE_BASE` for mirroring.

**Nothing objectionable enough to refuse on**, with the soft-checksum branch noted as a real
weakness: a network blip degrades a verified install to an unverified one without saying so.
The binary that actually landed does match the published digest, checked above.

## 3. The central claim: first call vs second call, from this machine

**CLI, cold ledger, live Jev backend** (`JEVCACHE_DIR=/tmp/jevcache-eval/ledger2`), wall time
measured around the whole process including spawn:

```
run 1  wall=   894.7ms  {"answers":{"argument":{"noul":0.67}},"cached":false,"source":"jev-1.13.0"}
run 2  wall=     8.8ms  {"answers":{"argument":{"noul":0.67}},"cached":true, "source":"jev-1.13.0"}
run 3  wall=     5.7ms  {"answers":{"argument":{"noul":0.67}},"cached":true, "source":"jev-1.13.0"}
```

**In-process, `jevcache serve --port 9334` with the same backend**, which removes process spawn
from the measurement:

```
POST /decide run 1    553.10ms  cached=False  answers={"argument":{"noul":0.71,"type":"noul"}}
POST /decide run 2      0.52ms  cached=True   answers={"argument":{"noul":0.71,"type":"noul"}}
POST /decide run 3      0.51ms  cached=True   answers={"argument":{"noul":0.71,"type":"noul"}}
```

**The central claim reproduces.** 553.10ms → 0.52ms, a 1064× reduction, and the repeat costs
nothing because no request is made. Confirmed further: with the network **fully denied**
(`sandbox-exec -f deny-net.sb`), both `recall` and `decide` returned the cached answer at rc=0.
Offline replay is real.

## 4. The `/decide` contract does not match the documented example

The landing page shows `body: JSON.stringify({ schema, state: ticket })` with a bare inline
schema. Posted verbatim against a live `serve`, three rejections in sequence:

```
site example (bare schema, no id/version)     HTTP 400 {"error":"schema.id must be a non-empty string"}
id only                                       HTTP 400 {"error":"schema.version must be an integer >= 1 (failure.argument)"}
id@version string                             HTTP 400 {"error":"schema.id \"failure.argument@1\" is invalid — use letters, digits, dot, dash, underscore"}
```

`{id, version, questions}` with `version` an integer works. Independently reproduced by the
conductor before this run. The documented example does not run.

Two more contract mismatches:
- README's config table says the `jev` backend key is `TYPESAFE_API_KEY`. The binary reads
  **`JEV_API_KEY`** (string present in the binary; `TYPESAFE_API_KEY` is not).
- `./jevcache.schemas.json` must be a **JSON array** of schema objects. An object-keyed map —
  the shape the docs' prose suggests — is **silently ignored**: `jevcache schemas` prints an
  empty list, no parse error, no warning. Two wasted attempts before the array shape was found.

## 5. THE DECIDING TEST — three cached vs three direct, same state, side by side

State: the exact object `work/omp-jev-failure/measure.mjs` builds for
`permission-denied-system-path` (`toolName: write`, `args.path: /usr/lib/jev-config.json`,
`failure: EACCES: permission denied, open '/usr/lib/jev-config.json'`). Question text copied
verbatim from `QUESTIONS.argument`.

| run | **jevcache** (`decide`, same ledger) | **direct `askJev`** (single question) | **direct `askJev`** (all three questions, harness shape) |
|---|---|---|---|
| 1 | `argument = 0.67` (miss → jev-1.13.0, 894.7ms) | `argument = 0.69` (496ms) | `transient 0.17  argument 0.68  bug 0.21` (611ms) |
| 2 | `argument = 0.67` (**cached**, 8.8ms) | `argument = 0.67` (715ms) | `transient 0.17  argument 0.66  bug 0.22` (1064ms) |
| 3 | `argument = 0.67` (**cached**, 5.7ms) | `argument = 0.66` (970ms) | `transient 0.16  argument 0.66  bug 0.21` (155ms) |

And the same three-question schema through jevcache, for a like-for-like:

| run | jevcache, three-question schema |
|---|---|
| 1 | `transient 0.14  argument 0.70  bug 0.23` (miss, 876.1ms) |
| 2 | `transient 0.14  argument 0.70  bug 0.23` (**cached**, 6.7ms) |
| 3 | `transient 0.14  argument 0.70  bug 0.23` (**cached**, 9.0ms) |

**CONFIRMED.** jevcache returns byte-identical answers across all three runs. The direct client
drifts on every question on every run: `argument` moved 0.69 → 0.67 → 0.66 single-question and
0.68 → 0.66 → 0.66 three-question; `transient` moved 0.17 → 0.17 → 0.16; `bug` moved
0.21 → 0.22 → 0.21. Spread is small — about ±0.03 — and that is precisely the size of the
effect the harness exists to detect.

Two honest qualifications:

1. **The 0.47/0.50/0.48 flip did not reproduce today.** On this run `argument` on
   `permission-denied-system-path` sits at 0.66–0.70, comfortably above the 0.50 threshold, so
   the HIT→MISS→MISS flip recorded under `omp-jev-failure` is not visible in today's numbers.
   That is itself worth knowing: the case has moved roughly +0.18 since that receipt, and the
   receipt's specific instability is not a stable property of the case. What *is* stable is the
   ±0.03 per-run drift, which is exactly enough to flip any question whose score lands in
   0.47–0.53.
2. The measured drift is between *sequential* calls in one session; it is not decomposed into
   model nondeterminism versus anything else. The harness does not care which it is — it cares
   that repeated identical calls do not return the same number, and they do not.

**What this settles.** Every `measure*.mjs` in this lane runs N times on byte-identical input
*in order to observe that spread*. Under jevcache, run 1 pays and runs 2..N replay it: spread
becomes exactly 0.00, `thin` verdicts vanish, and the harness reports perfect stability about a
question that is not stable. The failure mode is not "the cache is wrong" — the cache is
faithful. The failure mode is that **the cache is an oracle that answers the harness's question
before the harness asks it**, and answers it "stable" by construction. A measurement that cannot
fail is not a measurement.

**Ruling: the measurement harness may never run through jevcache, at any setting, including a
warm-once-then-measure setting.** There is no flag that helps; `recall` exits 3 on a miss and
`decide` is the only path that reaches the model, so there is no "bypass cache but keep the
client" mode. If a measurement needs the cache off, it must not use the binary.

## 6. What is actually on disk — the finding that matters tonight

`~/.jevcache/` is a single directory holding a single append-only file, `ledger.log`, mode
**`-rw-r--r--` (world-readable)**, JSONL. After one real decision, the `put` row is:

```json
{"t":"put","r":{
  "fingerprint":"14efe5c6…","model":"default","schema_id":"failure.all3","schema_version":1,
  "answers":{"argument":{"noul":0.7,…}},"source":"jev-1.13.0",
  "created_at":"2026-09-20T03:04:56.878Z","hits":0,
  "state_preview":"{\"args\":{\"path\":\"/usr/lib/jev-config.json\"},\"failure\":\"EACCES: permission denied, open '/usr/lib/jev-config.json'\",\"toolCallId\":\"measure-permission-denied-system-path\",\"toolName\":\"write\"}"
}}
```

**It is not hash-only. Every decision appends `state_preview`: the first 200 characters of the
canonicalized state, in plaintext.** The same is true on the `serve` path, not just the CLI.

The redactor runs first, and it does something — but it knows only four things, extracted from
the binary:

| rule | effect |
|---|---|
| `(?i)[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}` | → `<email>` |
| `(?-u)\+?[0-9][0-9\s().\-]{6,}[0-9]` | → `<phone>` |
| `(?-u)\b[0-9]{9,}\b` | → `<num>` |
| field names matching `(?i)(^\|_)(id\|uuid\|guid\|timestamp\|ts\|created_?at\|updated_?at\|time\|datetime\|date\|nonce\|session_?id\|request_?id\|trace_?id\|span_?id)$` | dropped from the key |

**There is no rule for credentials.** Probed with a synthetic state carrying an `Authorization:
Bearer` header in a command, an AWS-style secret, a synthetic `sk-live-…` value under the same
variable name our client reads, and a `.env` diff. The 200-character preview written to disk:

```
{"args":{"command":"curl -H 'Authorization: Bearer sk-ant-api03-REDACTEDLOOKALIKE-xyz789' https://api.typesafe.ai/v1/systemone -d @payload.json"},"contact":{"account":"<num>","email":"<email>","phone"
```

The email, phone and 12-digit account **were** masked. The bearer token was written **in full,
verbatim**. Redaction here means "PII-shaped tokens", not "secrets".

And the real ledger on this machine already demonstrates the mechanism with real inputs — read
read-only, from the conductor's own probing minutes earlier:

```
PUT state_preview: "{\"command\":\"chmod -R 777 /etc/passwd\"}"
PUT state_preview: "{\"command\":\"rm -rf /\"}"
```

Those two are harmless test strings. The point is the shape: **the command text is the thing
being stored.** Point the DCG harm classifier at the 813 real blocked commands pane 3 withheld
from a receipt today and every one of them lands, verbatim to 200 characters, in a
world-readable file that nothing rotates, truncates, or encrypts. `jevcache` has no `clear`, no
retention setting, and no `--no-preview`. Deleting is `rm ~/.jevcache/ledger.log`, which also
deletes the cache.

**This is the tonight-item.** It is not a reason the tool is bad; `state_preview` is obviously
there to make `stats`/debugging legible. It is a reason the tool cannot be pointed at anything
in this lane that handles commands, diffs, or environment without that field being disabled
upstream or the ledger being treated as a secret-bearing artifact.

## 7. What crosses the wire — the network half of the privacy claim holds

Two instrumented runs with `JEVCACHE_API_URL` pointed at a local logging HTTP server.

**Nothing is transmitted without an explicit command.** Ran `demo`, `schemas`, `stats`,
`recall`, `decide`, `publish` (local) with the commons pointed at the sniffer:

```
commons requests observed: 0
```

Corroborated by the `sandbox-exec` network-deny run in §3, which completed normally, and by the
binary's string table: the only hosts in it are `api.typesafe.ai/v1/systemone` (the backend you
configure), `jevcache.sh/api` (the commons), `gist.github.com` (publish `--gist`), and
`127.0.0.1:8080/v1/decide` (the default `local` backend). The install-time counter lives in the
shell script, not the binary.

**When you do reach the commons, only a fingerprint goes.** `jevcache use`:

```
POST /api/v1/recall
  {"fingerprint":"cfbe8550…","model":"default","schema_id":"failure.argument"}
```

`jevcache publish --remote` (stub returning a key, so the full sequence ran):

```
POST /api/v1/keys        {}
POST /api/v1/schemas     {"schema":{"id":"failure.argument","questions":{"argument":{"instructions":"Does this error tie to …","type":"noul"}},"version":1}}
PUT  /api/v1/decisions   {"answers":{"argument":{"noul":0.49,…}},"fingerprint":"cfbe8550…","model":"default","schema_id":"failure.argument","schema_version":1}
PUT  /api/v1/decisions   {"answers":{"argument":{"confidence":0.9,"value":true}},"fingerprint":"5318d044…",…}
```

Explicit leak check against the wire bodies: `sk-ant-api03`, the AWS-style secret, the synthetic
`sk-live-…` value, `OPENAI_API_KEY`, `state_preview`, `Authorization: Bearer` — **all absent**.
The claim "only a fingerprint and the answer ever leave your machine" is **true as stated**.

Three caveats the site does not put next to it:

- **The schema goes too.** `POST /v1/schemas` pushes the full question text. In this lane the
  question wording *is* the work product — it is what `question-shape`, `route-questions-measure`
  and every `measure*.mjs` exist to produce. Publishing a cache publishes the questions.
- **Fingerprints are enumerable by default.** There is no salt unless a schema sets one, and the
  input is a *redacted, canonicalized* state — a small, guessable space for things like
  `{"command": "<some command>"}`. Anyone with the commons can confirm whether a given command
  was decided. The site acknowledges per-schema salt exists; nothing makes you use it.
- The minted write key lands at `$JEVCACHE_DIR/apikey`, also mode `0644`.

## 8. Four more defects found while running it

**8.1 — The backend is not part of the cache key: a mock answer is served as a real one.**
Fresh ledger, one `decide` with `JEVCACHE_BACKEND=mock`, then three with `JEVCACHE_BACKEND=jev`
and a live key:

```
run 1  wall=5.9ms  {"answers":{"argument":{"confidence":0.9,"value":true}},"cached":true,"source":"mock"}
run 2  wall=5.7ms  … "cached":true,"source":"mock"
run 3  wall=5.5ms  … "cached":true,"source":"mock"
```

Identical fingerprint to the live-backend run (`5318d044…`). The mock's stub answer
(`value:true, confidence:0.9`) was served, three times, to a caller configured for the real
model. `source` records the truth but nothing acts on it. One `jevcache demo`-style exploration,
or one CI run with `mock`, permanently poisons the production cache for that state — and §7
shows `publish --remote` will then push the mock answer to a shared global index under the same
`model:"default"` as the real ones.

**8.2 — The default cache key does not contain the model version.** The `put` row records
`"model":"default"` even though `source` is `jev-1.13.0`. Passing `--model` explicitly *does*
enter the key (`--model jev-1.13.0` → `2579eb78…`, `--model jev-0.0.1-fake` → `a8b5a4db…`, no
flag → `5318d044…`, all distinct). So in the default configuration a jev-1.13.0 → 1.14.0 upgrade
does **not** invalidate anything: yesterday's model's answers keep being served forever. The
site sells this as "no model-version drift". It is not prevention, it is concealment — and it is
the same property that makes the cache lethal to measurement (§5).

**8.3 — Redaction silently collides distinct states.** Fingerprints of nine states, mock backend:

```
A id=prod          203a8ece2e9dcbab      C acct 123456789   bee42682a1413fd8
B id=staging       203a8ece2e9dcbab      D acct 987654321   bee42682a1413fd8

E date 2026        fd684a6789feca90      H to josh@…        e68816a5fae3ab97
F date 2099        fd684a6789feca90      I to attacker@…    e68816a5fae3ab97
G no date          fd684a6789feca90
```

`terraform apply` against **prod** and against **staging** are the same cache key. Two different
9-digit data paths are the same key. Three different dates, including absent, are the same key.
Two different mail recipients are the same key. The volatile-field rule is keyed on *field
names*, so anything your state calls `id`, `date`, `ts`, `nonce`, `session_id`, `trace_id`
stops existing for cache purposes. This is the demo's advertised behaviour, generalized: it is
right for a support ticket whose id is noise and catastrophically wrong for a safety gate whose
`id` is the blast radius.

**8.4 — One global ledger, no isolation, no locking.** The default is a single append-only
`~/.jevcache/ledger.log` shared by every process on the machine. During this evaluation I
found rows in it I had not written (the conductor's `harm@1` probing, minutes earlier) — which
is exactly the mechanism: **agent A's cached answer silently becomes agent B's result.** For a
lane running three panes plus background agents against one host, that is a correctness hazard,
not a nicety: a measurement run would inherit another agent's decisions, from another backend
(8.1), under another model (8.2), and report them as its own.

`JEVCACHE_DIR` **is** sufficient isolation *mechanically* — every ledger in this evaluation was
scoped with it and none of them saw each other's rows. But it is a **convention nobody is forced
to follow**: the default is shared, nothing warns, and a single forgotten export silently merges
two agents' caches. Isolation that depends on every caller remembering an env var is not
isolation; it is a habit. If this is adopted, `JEVCACHE_DIR` must be set by the extension code
itself, not by the operator's shell.

Minor, but confusing enough to cost time: the `hit` field in `decide --json` is `true` on a
**miss** and `false` on a **hit** (`cached` is the field that means what you think `hit` means).

## 9. Verdict, scoped

**ADOPT NARROWLY.** The product works, the central claim is real (553ms → 0.52ms, §3), offline
replay is real, and the network privacy claim is true as written (§7). It is defeated for us not
by any of that but by four properties that are each individually disqualifying for specific
surfaces.

Preconditions on *any* adoption here, all four:
1. `JEVCACHE_DIR` set **in extension code**, one ledger per extension, never the default (8.4).
2. `--model`/`model` always passed explicitly so the model version enters the key (8.2).
3. `JEVCACHE_BACKEND=mock` never run against a ledger any extension reads (8.1).
4. The ledger treated as a **secret-bearing artifact** — outside the repo, not world-readable,
   and excluded from any bundle — until `state_preview` can be disabled upstream (§6).

Of the nine extensions, two never call Jev and are out of scope by construction:
`omp-jev-preaction` (regex-only by measured ruling — four regexes beat the model 12/12 to 11/12)
and `omp-jev-observer`'s trigger path. The seven that call `askJev`:

**May use it** (repeat-heavy, state carries no credentials, a stale answer is a cosmetic loss):
- **`omp-jev-route`** — the strongest candidate. It scored the same turn 24 times; the decision
  is advisory hardness, never acts, and the state is turn metadata.
- **`omp-jev-rerank`** — identical search output reranks identically; observe-only; a stale
  ordering is harmless.
- **`omp-jev-foreman`** — fires on a repeat-command trigger, so its inputs are repeats by
  definition; observe-only.

**Must not use it:**
- **`omp-jev-observer`'s `classify-systemone.mjs`** — it classifies commands for *secret
  staging* and *privilege widening*. Its state is the command. §6 writes the command to disk in
  plaintext, and 8.3 collapses prod and staging to one key. Both failure modes are aimed exactly
  at what this surface exists to catch. Absolute no.
- **`omp-jev-commit` and `omp-jev-review`** — their state is a **diff**. Diffs are where
  credentials actually leak in this lane, and a 200-character plaintext preview of a diff is a
  secret-disclosure surface with no upside: diffs are near-unique, so the hit rate approaches
  zero and the only thing the cache reliably produces is the on-disk copy.

**Undecided, needs its own measurement, do not adopt on this receipt:**
- **`omp-jev-failure`** and **`omp-jev-dispatch`**. Both are plausible on repeat-rate, but
  `failure` is the extension whose own harness this cache would break (§5), and `dispatch`
  packets contain instructions that can carry paths and commands. Neither is urgent.

**And the ruling that matters most: the measurement harness may never run through jevcache.**
Not `measure.mjs`, not `measure-multiclass.mjs`, not `measure-realdiffs.mjs`, not
`question-shape-measure.mjs`, not any future `measure*.mjs`. Their N-run design exists to observe
the ±0.03 spread quantified in §5; a cache replaces that spread with 0.00 and converts an
unstable question into a certified-stable one. If jevcache is adopted for the three extensions
above, the harness must call `askJev` directly — which it already does, and which is now a
load-bearing reason not to "unify" the two paths later.

Two things worth sending upstream, as defects rather than opinions: the soft-checksum branch in
the installer (§1), and the mock-poisons-production key (8.1), which is a correctness bug by any
reading.

## NO-CLAIM

One evaluation, one machine, one evening, one API key, version 0.1.0.

This does not establish a **hit rate** on our real traffic: every repeat measured here was one I
constructed by running the same file twice. The site's 78% recurrence and the "$4,704/month"
figure are untested here and nothing above supports or refutes them; the three extensions named
adoptable are named on the *shape* of their inputs, not on a measured repeat rate, and that
measurement has not been done.

It does not establish that **`state_preview` is the only place raw state lands**. I read
`ledger.log`, the `shared/` bundle, and the wire on `use` and `publish --remote`. I did not
decompile the binary, did not exercise `add`, `replay`, `market`, `usage`, `earnings` or
`wallet`, and did not test the real hosted index end-to-end — `publish --remote` was pointed at
a local stub deliberately, so what the live commons does with an upload is unverified.

It does not establish that the **drift I measured is model nondeterminism**. Three runs per
condition, one session, one afternoon, one model version. Three runs cannot distinguish
nondeterminism from a slow drift in the backend, and the fact that `argument` on this case sits
0.18 higher today than in the `omp-jev-failure` receipt is unexplained by anything here.

It does not establish that the **collisions in 8.3 occur in our real states**. They are synthetic
states I wrote to hit the documented rules. Whether any of the nine extensions actually emits a
field named `id`/`date`/`ts` at a position where collapsing it changes the answer was not
audited state-by-state.

It does not establish anything about **Linux, x64, or a fresh install**: the binary tested is the
one already on this machine, and the installer was read but not executed for this document.

Finally, the network findings in §7 are from an **instrumented localhost stub**, not a packet
capture. They prove the binary sends what it sends to the URL it is told to use, and the
`sandbox-exec` deny-network run proves the hit path needs no network. They do not prove the
absence of some egress path neither the string table nor these six commands touched.
