# jev-cz0 re-census: commit, review and rerank have no real traffic to label (2026-09-24)

Bead `jev-cz0` asks for a labels file per extension (commit, review, rerank), with precision and
recall on real traffic. RedMaple reopened it (R97 audit, `jev-puyn`). The condition for closing it
is a labels file per extension, or a committed finding that there is nothing real to label. This is
the finding, re-measured today. The 2026-09-19 census is in `cz0-labels-20260919.md`.

## Command

```
python3 work/omp-jev-review/cz0-census.py
```

It is keyless and offline. It scans every omp session transcript on this machine: the default agent
root plus every profile root, 2,126 files under 9 roots. A row counts only after its JSON line
parses. It counts `customType` decision entries for review and commit, and `toolCall` parts named
`jev_rerank` for rerank.

**Instrument check.** The same parser finds 1,021 `bash` tool calls and 1,020 `bash` results in
pane 1's own transcript. An absence reported by this parser is therefore not a wrong path.

## Result

| Extension | Decision rows | From real traffic | Where the rows come from |
|---|---:|---:|---|
| commit (`omp-jev-commit`) | 0 | 0 | never registered in any omp config |
| review (`omp-jev-review`) | 17 | 0 | 3 `review_error` (`systemOne HTTP 400`) from one `/tmp` session on 2026-09-20; 14 from L3 probe sessions in `/tmp/review-l3` |
| rerank (`jev_rerank` tool) | 0 calls | 0 | every mention in a transcript is prose, not a tool call |

- **Commit.** The 31 labels in `work/omp-jev-commit/labels-cz0.jsonl`, with precision and recall in
  `commit-judge-31-20260919.md`, are offline labels on commit diffs. No live decision row exists to
  label.
- **Review.** The only omp config that loads it is `~/.omp/profiles/jev-lab/agent/config.yml`. Both
  worker panes run `--profile grok`. None of the 17 rows comes from work traffic.
- **Rerank.** The tool is registered in this project's `.omp/config.yml`, but no agent has ever
  called it. A labels file for it would be empty by construction.

## Finding: the L3 probe loaded the review extension twice

The 14 L3 rows are 7 decisions, each recorded twice with the same `toolCallId`. In the session with
the code diff, the review extension's diagnostic and decision entries appear once before and once
after `omp-guard-rule`'s entries for that same call (session `01a0d10e`, lines 5-6 and 9-10). Its
two `review_scored` rows have different latencies (354 ms and 201 ms), so Jev was asked twice.

Cause: `/tmp/review-l3/.omp/extensions/omp-jev-review` is a symlink to
`work/omp-jev-review` (project discovery), and each run also passed
`-e /Users/josh/Developer/jev/work/omp-jev-review/src/index.ts`. omp loaded both paths.

`omp-jev-review-detgate-20260924.md` reports "2× `review_scored`" and "2 Jev calls". That is one
decision scored twice, not two decisions. It does not change that receipt's verdict: applicability
is deterministic, and the scores are the same (0.05 and 0.03 on both).

## What would make labelling possible

Install review and rerank where the fleet actually runs: the project `.omp/config.yml`, or the grok
profile. Then let real sessions produce rows, and label them before looking at any score. Until
then, precision and recall on "real traffic" cannot be measured for these two, and commit's 31
offline labels are its only evidence.

NO-CLAIM: our traffic is not a stranger's. This census counts rows; it grades nothing. The double
load was read from one session file and its launch commands; omp's extension de-duplication was not
tested directly.
