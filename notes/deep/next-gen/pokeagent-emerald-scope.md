**Date:** 2026-09-25
**State:** `PROBED` keyless; ROM build `live-local` (no Jev/VLM call)
**Question:** Can Jev play the full Pokémon Emerald RPG through the PokéAgent Challenge harness on this Mac?

## Verdict

**Yes, conditionally.** The official/reference harness is `sethkarten/continual-harness` at **v5.0.0 / `62bf6f614b66ff76b79954e5a3f04f91c3c6a049`**, MIT. ## What the harness exposes

The direct server state is a JSON object with these top-level sections:

```json
{
  "visual": {"screenshot": "<image>", "resolution": [240, 160]},
  "player": {
    "position": {"x": 0, "y": 0},
    "location": "Littleroot Town",
    "name": "...",
    "party": [],
    "inventory": {}
  },
  "game": {
    "money": 0,
    "game_state": "overworld",
    "is_in_battle": false,
    "time": [0, 0, 0],
    "badges": 0,
    "items": [],
    "item_count": 0,
    "pokedex_caught": 0,
    "pokedex_seen": 0,
    "battle_info": {},
    "dialog_text": "",
    "dialogue_detected": {"has_dialogue": false, "confidence": 0.0},
    "progress_context": {}
  },
  "map": {
    "tiles": [[...]],
    "tile_names": [[...]],
    "metatile_behaviors": [[...]],
    "metatile_info": [[...]],
    "object_events": [],
    "visual_map": "..."
  }
}
```

`memory_reader.py` reads a 15×15 tile neighborhood, player coordinates/location, party fields (species, level, HP, status, types, moves, PP, nickname), inventory, battle information, dialogue detection, and milestone-related progress. The external MCP proxy intentionally removes `raw_state` and returns `state_text` plus a PNG screenshot; a Jev adapter should call the direct server or construct a compact JSON projection rather than send the image/base64 and full tile matrices on every call.

**Proposed Jev per-tick projection:** retain `tick`, `step_number`, `mode` (`overworld|dialog|battle|menu`), `player.location`, `player.position`, `player.party`, the relevant `game.battle_info`/`dialog_text`, `map.visual_map` plus nearby passability, ordered milestone progress, and the last 8 actions. Omit the screenshot, full raw tile arrays, and long inventory/map caches unless a separate recovery question requests them. The projection is our adapter design, not an upstream contract.

## Choice and action timing

Use one Jev **Choice** per decision tick. The initial action labels are the 11 valid Emerald button macros exposed by the server:

`A`, `B`, `START`, `SELECT`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `L`, `R`, `WAIT`.

The adapter maps exactly one label to `press_buttons([label], speed=...)`; it MUST reject unknown labels rather than inherit the upstream endpoint's unsafe invalid-button fallback to `A`. Later, context-specific macros such as `ADVANCE_DIALOGUE -> [A] / fast` or `MOVE_UP -> [UP] / normal` can reduce option ambiguity, but a long route macro trades fewer Jev calls for larger open-loop failure windows.

The server loop targets `80` frames/s. Presets are:

| preset | hold + release | source rate at 80 FPS |
|---|---:|---:|
| `fast` | 6 + 3 = 9 frames | 8.89 decisions/s |
| `normal` | 10 + 8 = 18 frames | 4.44 decisions/s |
| `slow` | 16 + 16 = 32 frames | 2.50 decisions/s |

During cached dialogue, the source multiplies the loop rate by four (`320` frames/s), so a `fast` stream could demand 35.56 decisions/s. TypeSafe's **1,200 requests/minute = 20 requests/s** hard cap therefore requires a limiter. The safe policy is: one Jev request per completed macro, a minimum 50 ms inter-request interval, and hold the last safe action or `WAIT` while the limiter is full. At normal movement speed the harness is below the cap; only dialogue acceleration or an unbounded caller can saturate it. Do not ask Jev once per emulator frame.

The request shape follows the local SDK surface: `systemOne({state, questions: {action: choice(...)}})` and read `answers.action.choice`, `answers.action.confidence`, and `answers.action.probabilities`. The policy should act only above a preregistered confidence threshold; low confidence, malformed answers, transport failure, or rate-limit exhaustion means `WAIT`, not a guessed button.

## Rules and scoring boundary

The official Track 2 rules require interaction through the custom emulator API, final actions generated by a neural network, action/state logs, and complete video; evaluation uses milestone completion, elapsed time, action count, and reproducibility. The first-gym milestone used by the harness is the `STONE_BADGE` after Rustboro. The harness's ordered milestones include `GAME_RUNNING` through `RUSTBORO_GYM_ENTERED` and `STONE_BADGE`. This note is a feasibility design, not a competition submission; formal organizer instructions outrank this summary.

Cheapest experiment: run the stored ROM in a Docker arm64 copy of the harness, use the compact state projection and one 11-way Choice per macro, stop at `STONE_BADGE`, and compare wall-clock plus action count against a deterministic route under the same emulator. Record trajectory, state/action logs, and video. No paid comparator or Jev call was made in this scope.
